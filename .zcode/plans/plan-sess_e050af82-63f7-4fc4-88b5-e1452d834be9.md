# Playtest Roadmap — Final Three Items: §5 Card Tokens, §6 Clone, §10 Turn Phases

Implements the rest of `2026-08-20-playtest-feedback-roadmap.md` in its recommended order: §5+§6 together (both ride `relatedTokens`/`CREATE_TOKEN` and share the cache bump), then §10 (largest — touches shared protocol, engine, UI, keybinds). Everything stays state-sync + UI: no rules enforcement anywhere.

## Part A — §5+§6 data layer (`frontend/src/lib/scryfall.ts`, `cardCache.ts`)

1. `ScryfallCard` gains `all_parts?: Array<{ id: string; name: string; component: string; type_line?: string }>`.
2. New exported pure helper (unit-testable):
   ```ts
   /** Tokens/emblems a card creates, from Scryfall's all_parts — parts whose
    *  component is "token" or whose type_line starts with Token/Emblem
    *  (belt and braces across Scryfall's part typing). Deduped by id, capped at 8. */
   export function relatedTokensOf(card: { all_parts?: ... }): { id: string; name: string }[]
   ```
   Filter: `part.component === "token" || /^(token|emblem)/i.test(part.type_line ?? "")`; dedupe by id; `.slice(0, 8)`.
3. `CardDef` gains `relatedTokens: { id: string; name: string }[]` (required — `toDef` is the only constructor, sets it via `relatedTokensOf(card)`). Fix any compile fallout if a test constructs a `CardDef` literal.
4. **Bump card cache version** `mtg:cards:v2` → `mtg:cards:v3` in `cardCache.ts:9` + comment (AGENTS.md rule: required whenever CardDef's shape changes). Old cache is dropped; defs re-resolve lazily via `useCardDefs`/DeckLoader.
5. **Tests** — extend `frontend/src/lib/scryfall.test.ts`: `relatedTokensOf` filters `component:"token"`, catches `type_line` "Token Creature — Goblin" and "Emblem — Jace", dedupes, caps at 8, ignores `combo_piece`/`meld_part` parts, returns `[]` with no `all_parts`.

No server changes: `CREATE_TOKEN` (`server/src/engine/actions/cards.ts:143-182`) already accepts an arbitrary client-supplied `cardId`, validates count 1–20 (`MAX_TOKENS_AT_ONCE = 20`, `internal.ts:43`), spreads positions, and logs chat. Token art on every client resolves automatically: the new snapshot exposes the token's `cardId` on the battlefield → `GameTable`'s `cardIds` memo → `useCardDefs` fetches and caches it.

## Part B — §5+§6 UI (ContextMenu, CountPickerModal, GameTable)

**Open the context menu on opponents' battlefield cards (§6's "any player's card")** — today `openCardMenu` bails for non-own cards (`GameTable.tsx:351-365`):
- `MenuState`'s card entry gains `own: boolean`. `openCardMenu`: keep `findOwnCard` for own cards; if not own but `onAnyBattlefield(view, uid)`, open with `{ own: false, zone: "battlefield" }`.
- `ContextMenu.tsx`: when `!menu.own`, render a **reduced menu** containing only "Create token…" (if the def has related tokens) and "Clone…" (if `cardId !== null`) — every other item (QUICK actions, tap/flip/arrow/attach/counters/notes/move/reveal) renders only for own cards. Server ownership checks are the backstop; the UI just doesn't offer actions that would bounce.

**"Create token…" submenu (§5):**
- ContextMenu gains prop `getDef: (id: string | null) => CardDef | null` (GameTable passes its existing `get`; useCardDefs has usually already cached every battlefield card's def, and re-renders flow through since ContextMenu isn't memoized).
- For battlefield cards (own or the reduced opponents' menu) where `getDef(card.cardId)?.relatedTokens.length > 0`: a "Create token…" toggle (same pattern/styling as the existing "Move to…" toggle at lines 279-298 — new `tokenOpen` state added to the render-time reset alongside `moveOpen`). Expanded: one button per related token, labeled with its name.
- Picking one calls new prop `onCreateToken(token: { name: string; cardId: string })` and closes the menu.

**"Clone…" (§6):**
- New prop `onClone(card: CardView)`. Menu item on face-up battlefield cards (`card.cardId !== null`), own full menu and opponents' reduced menu. Face-down cards (`cardId === null`) hide it.

**CountPickerModal**: `PickerMode` adds `"token" | "clone"`. `PickerConfig.confirm` signature widens to `(n: number, subject?: string) => string` (existing entries unaffected); new CONFIG entries — token: title "Create tokens", confirm `(n, s) => "Create " + n + " × " + (s ?? "token")`; clone: title "Clone card", confirm `(n) => "Clone × " + n`. New optional `subject?: string` prop displayed in the title row (e.g. "Create tokens — Goblin").

**GameTable wiring**:
- New state `pickerCreate: { name: string; cardId?: string } | null` alongside the existing `picker` mode state (set together for token/clone, cleared on close/confirm; all other `setPicker` call sites unchanged).
- `pickerMax`: `case "token": case "clone": return 20;` (server cap; larger X via existing Ctrl+G repeat-last).
- `confirmPicker`: token/clone → `send({ type: "CREATE_TOKEN", name: pickerCreate.name, cardId: pickerCreate.cardId, count: n })` **and `setLastToken(...)`** so "create another" (Ctrl+G) repeats it — that's the doc's ">20 via repeat" path.
- `initial={picker === "mulligan" ? hand.length : 1}` unchanged (token/clone default 1).
- Wire ContextMenu props: `getDef={get}`, `onCreateToken={(t) => { setPickerCreate(t); setPicker("token"); }}`, `onClone={(card) => { setPickerCreate({ name: get(card.cardId)?.name ?? "Card", cardId: card.cardId ?? undefined }); setPicker("clone"); }}`.

## Part C — §10 phases: shared + server

**Shared (`shared/src/index.ts`)** — mirror the `ALL_ZONES` pattern (lines 16-24):
```ts
export type Phase =
  | "untap" | "upkeep" | "draw" | "main1"
  | "startCombat" | "attackers" | "blockers" | "damage" | "endCombat"
  | "main2" | "end";
export const ALL_PHASES: Phase[] = [ /* same order */ ];
```
Action union (next to `NEXT_TURN`): `| { type: "SET_PHASE"; phase: Phase }`. `GameView` gains `phase: Phase`. (tsc will flag any test mocks constructing full GameViews — fix as they surface.)

**Server:**
- `state.ts`: `Game` gains `phase: Phase`; `createGame` initializes `"untap"`.
- `game.ts`:
  - `START_GAME`: set `game.phase = "untap"` (explicit, covers post-END_GAME restarts).
  - `NEXT_TURN` (lines 79-94): keep round-robin + `game.arrows = []` + existing "It is now X's turn" chat (kept as-is — the doc's "— Ada's turn —" would just rename the existing line; not worth churn). Add: `game.phase = "untap"` and **untap every card on the incoming player's battlefield** (`for (const c of next.zones.battlefield) c.tapped = false;`) — the chosen convenience, deliberately dumb (cards that "shouldn't" untap get re-tapped by hand; no per-card logic ever).
  - New `setPhase` handler + `SET_PHASE` map entry: `requireStarted` + `ALL_PHASES.includes(action.phase)` — purely structural, **open to any seated player**, no active-player gating (consistent with NEXT_TURN).
- `admin.ts` `END_GAME`: also reset `game.phase = "untap"`.
- `view.ts` `personalize`: expose `phase: game.phase` (identical for every viewer).

**Server tests (`game.test.ts`):** SET_PHASE accepts a valid member and flips `game.phase`; rejects an unknown string (cast `as Phase`) and pre-game; non-active player may set it. NEXT_TURN: resets phase to "untap", untaps the incoming player's tapped battlefield cards (tap one of the next player's cards first), clears arrows (draw one via DRAW_ARROW first), chat line unchanged. `view.test.ts`: `phase` exposed in the snapshot.

## Part D — §10 frontend (PhaseBar, keybinds)

**New `frontend/src/components/game/PhaseBar.tsx`:**
- Props: `{ phase: Phase; activeName: string; isYou: boolean; onSelect: (p: Phase) => void; onNext: () => void }`.
- Slim strip (`h-7`, same visual family as the focus-mode bar in `Battlefield.tsx:124-150`): active player's name at the left (emerald when it's you), then one small labeled button per phase — labels `Untap · Upkeep · Draw · Main 1 · Combat · Attack · Block · Damage · End Combat · Main 2 · End` (`PHASE_LABELS: Record<Phase, string>` local to the file; active phase emerald-highlighted, `bar-in` entrance like the other bars) — and a **"Next ▸"** button at the right.
- Placement: in `GameTable`'s center column, rendered between `Battlefield` and the mode bars (select/arrow/attach), i.e. docked directly above `HandFan` — visible in every non-maximized mode (the maximize overlay skips it; Esc exits). Pure presentation; clicking sends actions via callbacks.

**GameTable wiring:**
- `const active = view.players.find(p => p.id === view.activePlayerId)` → `activeName`, `isYou`.
- `function nextPhaseAction(): Action` — `view.phase !== "end"` → `SET_PHASE` with the following `ALL_PHASES` entry; at `"end"` → `NEXT_TURN`.
- `<PhaseBar phase={view.phase} activeName={...} isYou={...} onSelect={(p) => send({ type: "SET_PHASE", phase: p })} onNext={() => send(nextPhaseAction())} />`.
- ChatPanel's existing "Next turn ⏭" button stays (direct pass-turn).

**Keybinds (`frontend/src/lib/keybinds.ts` + test):**
- Repoint **Ctrl+Enter** (`nextTurn`) to next-phase-or-turn: dispatcher case sends `nextPhaseAction()` instead of bare NEXT_TURN. Label becomes "Next phase / turn".
- New id **`passTurn`: "Ctrl+Shift+Enter"** (combo format already supported by `eventToCombo`; not browser-reserved) → sends `NEXT_TURN` directly. Add to `KeybindId`, `DEFAULT_KEYBINDS`, `KEYBIND_LABELS` ("Pass turn"), and the "Board & turn" `SHORTCUT_GROUPS` section — the Record types + coverage test (`keybinds.test.ts:120-131`) force completeness; add an `eventToCombo` assertion that Ctrl+Shift+Enter maps to `passTurn`.

**e2e (`server/scripts/e2e-m2.js`):** after the existing turn-pass check, host sends `SET_PHASE {phase: "main1"}`; assert **both** clients see `phase === "main1"` in their snapshots; then `NEXT_TURN` → both see `phase === "untap"`.
